# Midas Research Workspace

Standalone Svelte app, separate from `frontend/` (training UI) and `trader/` (terminal UI). The production workspace is served by the Rust trader, including its chart and strategy APIs. Bun and Vite are used to build the browser assets; they do not run on the production server.

From the repository root, build with `npm --prefix webui install`, `bun --cwd webui run build:rust`, and `cargo build --manifest-path trader/Cargo.toml --features web-ui`. Start the server with `MIDAS_LAN_HOST=192.168.1.57 ./trader/target/debug/trader web --listen 0.0.0.0:9757`, replacing the address with this computer's LAN address. Open that address and port in the browser. Without `--listen` the server binds to localhost only. To serve assets from another location, pass `--assets /absolute/path/to/dist-rust`.

The local APIs accept localhost by default. LAN access requires the explicit `MIDAS_LAN_HOST` address and a reachable listen interface. Devices able to reach the server can use it; the host and origin checks are not user authentication. The legacy SvelteKit server and `bun run dev` remain available during migration.

Upload a CSV with timestamp/date and open/high/low/close columns. Actual uploaded rows are rendered with TradingView Lightweight Charts (Apache 2.0; https://github.com/tradingview/lightweight-charts). Heikin Ashi is calculated locally as a chart-only transformation. Workspace settings are stored in localStorage on this device.

The local strategy API can discover, validate, run, and rank existing native replay sweep specifications. It uses the Trader replay CLI in offline mode and does not place orders. It only lists JSON specs found under `trader/.run/**/specs/`, rewrites each run's output directory into an isolated `trader/.run/webui-strategy-jobs/<job-id>/output`, validates with the native CLI before execution, and accepts no caller-supplied filesystem path or command-line fragment. Ranking writes a unique native `sweep-ranking.json` beneath that replay output, preserving the source summary and plan paths; the TUI analytics scanner can discover it under `.run` and its artifact remains available after a web server restart.

The Lua prototype panel uses the currently selected sweep as its replay base. Lua runs only in cached offline replay with an isolated, stateful sandbox per run. It uses closed bars; during history warmup, `ctx.is_warmup` is true and `ctx.position_qty` is unavailable. It accepts `POST /api/strategy/lua` with `{ "operation": "lua-validate" | "lua-run", "sweepId": "<catalog id>", "luaSource": "..." }`. The backend loads the selected catalog spec itself, keeps its dataset and replay/account settings, replaces the base strategy with the submitted Lua source, clears parameter dimensions and constraints to produce one run, forces `execution_mode: isolated_services` and closed-bar timing, and gives the job its own output directory. Source is capped at 12 KiB UTF-8; the JSON request is capped at 32 KiB. Lua runtime bounds are fixed at 8 MiB memory and 100,000 instructions per evaluation. Validation and replay use the same native CLI and single active-job gate as regular sweep jobs; the job can be polled and cancelled through the existing `/api/strategy/jobs/<id>` endpoints. A Lua replay is marked failed when its native summary reports a failed child, even if the CLI process exits zero. Successful Lua replay artifacts are available through `/api/strategy/jobs/<id>/results` and summarized in the panel. This route only invokes offline replay commands; it has no live-order path.

The sweep editor creates a new spec from the selected catalog base. It sends `POST /api/strategy/specs` with `{ "sourceSweepId": "<catalog id>", "name": "...", "parameters": [{ "path": "order_qty", "values": [1, 2] }] }`. The server resolves the source ID from the native catalog, clones that spec, changes only its name, generated sweep ID, parameter dimensions, and server-owned output path, then calls `validate-replay-sweep` before saving it under `trader/.run/webui-created/<generated-id>/specs/`. The endpoint accepts no filesystem path, native command fragment, dataset/strategy/account override, constraint, guardrail override, or execution request. Names are limited to 100 characters; at most 8 dimensions, 16 scalar values per dimension, and 32 Cartesian combinations are accepted. Native validation is authoritative for parameter path/type and spec validity. Any native guardrail violation or large-sweep confirmation warning prevents saving. Newly created specs appear in the existing catalog and can then use its ordinary native validate/run controls. This remains an offline replay workflow and does not place orders.

Run the focused policy and lifecycle checks with `node --test tests/lua-prototype.test.mjs tests/lua-replay-lifecycle.test.mjs` from `webui/`.

Sweep editor contract tests: `node --test src/lib/server/strategy-sweep-editor.test.mjs` from `webui/`.

Strategy API contract (localhost by default, or the explicitly configured LAN address):

- `GET /api/strategy` returns `{ sweeps, jobs }`. Each sweep has an opaque `id`, display `name`, native `sweepId`, and `datasetViewId`.
- `POST /api/strategy` accepts `{ "operation": "validate" | "run", "sweepId": "<catalog id>" }` or `{ "operation": "rank", "sweepId": "<catalog id>", "sourceJobId": "<completed run job id>", "metric": "robustness" }`. It returns HTTP 202 and a durable job record.
- `GET /api/strategy/jobs/<id>` returns job status, native sweep progress when present, and final CLI output. Completed ranking results also include `artifactPath`, `sourceSummary`, and `sourcePlan` when the source plan is available. Refresh the TUI Analytics view to load the saved ranking, then use its candidate import controls for the explicit strategy handoff.
- `DELETE /api/strategy/jobs/<id>` requests cancellation of the native process.

Completed native replay jobs expose `GET /api/strategy/jobs/<id>/heatmap?x=<parameter-path>&y=<parameter-path>&metric=<summary-field>`. The endpoint reads that job's `sweep-plan.json` and `sweep-summary.json` directly. Omit selectors to choose the first two parameter paths and `net_pnl` where available. Supported metrics are the numeric native summary fields `gross_pnl`, `net_pnl`, `fees`, `max_drawdown`, `trade_count`, and `fill_count`; only fields present as finite numbers in the summary are offered.

The response includes all distinct scalar parameter paths and values from native plan `children[].parameter_values`, a rectangular `cells` grid, and job counts. Every planned cell carries its exact candidate ID, run index, complete parameter-value map, outcome status, and selected metric when completed. A candidate missing from the summary is `missing_result`; native `failed` and `skipped` statuses stay distinct. A coordinate with no planned candidate is `planned: false`. Multiple candidates at one coordinate remain separate (for example when a third parameter is not on either axis), so the UI does not invent an aggregate. The workspace displays this heatmap for the selected completed replay job.

Only one strategy job can be active at a time. Ranking is restricted to completed runs launched by this API and to native metric names. The run command does not pass the CLI's large-sweep confirmation or guardrail override switches, so native guardrails can reject a selected spec. Job metadata survives web server restarts; jobs that were active during restart are marked failed and must be resubmitted. Progress is sampled from the native `sweep-status.json`; cancellation sends a termination signal and completion status comes from the process exit. Ranking artifacts and provenance are persisted in the job record and the native JSON file; no workflow runs automatically.

The **Live engine** source observes the currently subscribed chart on a running local trader engine. It sends no commands to the engine. The engine socket does not identify the broker or provide a market-data freshness timestamp, so neither is inferred. Set `MIDAS_ENGINE_SOCKET` to the absolute path of the engine socket when it differs from the default. This does not establish a separate NinjaTrader data connection.
